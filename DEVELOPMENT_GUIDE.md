# План дальнейшей разработки проекта

Дата: 2026-04-26

## 1) Цель этого гайда

Этот документ объясняет:
- **что делать** дальше, чтобы довести проект до рабочего MVP;
- **как делать** (пошагово, с примерами и критериями качества);
- **зачем делать** каждый шаг (какой риск он закрывает и какую пользу даёт).

Проект сейчас — это базовая статическая страница. Технические HTML/CSS-блокеры сняты, но до продуктовой готовности не хватает структуры, контента, процессов качества и релизной дисциплины.

---

## 2) Целевое состояние (куда идём)

Минимально достаточный результат (MVP):
1. Пользователь открывает страницу и сразу понимает назначение проекта.
2. Есть понятная структура: шапка, основной блок, секция «о проекте», контакты/футер.
3. Есть адаптивность под мобильные экраны.
4. В репозитории есть `README.md` с инструкцией запуска.
5. Настроены автоматические проверки (линтинг/валидация) в CI.
6. Любое изменение проходит через понятный pipeline: ветка → PR → проверки → merge.

---

## 3) Общий roadmap (по этапам)

### Этап A. Базовая инженерная гигиена (1 день)
**Что делать:**
- Добавить `README.md`.
- Ввести структуру директорий (`css/`, `assets/`, при необходимости `js/`).
- Добавить `.editorconfig` и базовые правила форматирования.

**Как делать:**
1. Создать `README.md` с разделами:
   - Описание проекта.
   - Как запустить локально.
   - Структура проекта.
   - План развития (кратко).
2. Зафиксировать соглашения:
   - Кодировка UTF-8.
   - Отступы (2 или 4 пробела, выбрать один стандарт).
   - Именование файлов (kebab-case).

**Зачем:**
- Новому участнику легче войти в проект.
- Снижается хаос и количество технического долга на ранней стадии.

**Критерий готовности этапа:**
- Любой человек может открыть репозиторий и за 3–5 минут понять, как запустить и куда вносить изменения.

---

### Этап B. Контент и UX-структура страницы (1–2 дня)
**Что делать:**
- Расширить `index.html` до полноценного каркаса лендинга.

**Как делать:**
1. Разметить страницу семантическими блоками:
   - `<header>`: название и краткий оффер.
   - `<main>`: ключевая польза/описание.
   - `<section>`: блоки «Преимущества», «Как это работает», «FAQ».
   - `<footer>`: контакты/копирайт.
2. Добавить заголовки (`h1`, `h2`) и короткие тексты для каждого блока.
3. Проверить логическую иерархию заголовков (только один `h1`).

**Зачем:**
- Пользователь должен понимать продукт за первые 5–10 секунд.
- Семантика улучшает SEO и доступность.

**Критерий готовности этапа:**
- На странице есть законченная структура и понятный сценарий чтения сверху вниз.

---

### Этап C. Стили и адаптивность (1–2 дня)
**Что делать:**
- Привести внешний вид к аккуратному MVP-уровню.

**Как делать:**
1. В `css/main.css` добавить:
   - Переменные цветов/отступов (`:root` с CSS custom properties).
   - Типографику (базовый размер шрифта, межстрочный интервал).
   - Сетку/контейнер (`max-width`, `margin: 0 auto`, `padding`).
2. Добавить media queries минимум для:
   - ≤ 768px (планшет/мобайл)
   - ≤ 480px (малые экраны)
3. Проверить контраст текста и фона.

**Зачем:**
- Без адаптивности проект выглядит «сломано» на мобильных.
- Системные стили ускоряют последующие итерации.

**Критерий готовности этапа:**
- Страница читаема и визуально стабильна на desktop и mobile.

---

### Этап D. Качество и автоматические проверки (1 день)
**Что делать:**
- Внедрить линтеры и CI.

**Как делать:**
1. Подключить инструменты проверки:
   - HTML-валидатор/линтер.
   - Stylelint для CSS.
   - Prettier (опционально) для единообразного форматирования.
2. Добавить workflow в GitHub Actions:
   - Запуск проверок на push/PR.
   - Блокировка merge при падении проверок.

**Зачем:**
- Ошибки ловятся до релиза, а не после.
- Единый стандарт качества для всех изменений.

**Критерий готовности этапа:**
- PR нельзя слить, пока не прошли все quality checks.

---

### Этап E. Релизный цикл и документация (0.5–1 день)
**Что делать:**
- Зафиксировать процесс выпуска изменений.

**Как делать:**
1. Добавить `CHANGELOG.md`.
2. Определить policy:
   - маленькие PR,
   - осмысленные commit-сообщения,
   - краткое описание «что/зачем» в PR.
3. Определить Definition of Done (DoD) для задачи:
   - код работает,
   - проверки зелёные,
   - документация обновлена.

**Зачем:**
- Проект становится предсказуемым в развитии.
- Упрощается сопровождение и передача контекста.

**Критерий готовности этапа:**
- Есть понятный регламент, который реально применяется на каждом PR.

---

## 5) Что не делать на текущем этапе

1. Не усложнять стек без необходимости (сразу не переходить на тяжелый фреймворк).
2. Не откладывать документацию «на потом».
3. Не смешивать большие несвязанные изменения в одном PR.
4. Не делать визуальные правки без проверки на мобильных.

---

## 6) Метрики прогресса (чтобы понять, что вы движетесь правильно)

Отслеживайте еженедельно:
- Количество открытых/закрытых задач по roadmap.
- Процент PR, прошедших проверки с первого раза.
- Количество регрессий после merge (должно стремиться к нулю).
- Время от создания задачи до merge (lead time).

---

## 7) Краткий итог

Если выполнить этапы A–E последовательно, проект перейдёт:
- из состояния «базовая статическая страница»
- в состояние «поддерживаемый MVP с понятной структурой, качеством и процессом поставки изменений».

Главный принцип: **сначала стабильная основа (документация + проверки), затем масштабирование функциональности**.
